<task type="auto">
  <name>Task 1: Migrate auth, items, and contacts actions to next-safe-action</name>
  <files>app/auth/actions.ts, app/items/actions.ts, app/contacts/actions.ts</files>
  <action>
Migrate all MUTATION actions in these 3 files to use next-safe-action. Leave QUERY actions (getGroupItems, getItemDetails, getUserItems, getBorrowedItems, getItemDetailsWithBorrow, getItemBorrowHistory, getContacts, searchContacts, getContactWithBorrowHistory, getPublicItemsForContact) as-is -- they are read-only and do NOT need migration.

**For each mutation action, follow this migration pattern:**

1. Replace `export async function actionName(args)` with `export const actionName = authActionClient.inputSchema(schema).action(async ({ parsedInput, ctx: { user, supabase } }) => { ... })`
2. Remove the manual `createClient()` call (use `ctx.supabase` from middleware)
3. Remove the manual `getUser()` + auth check (handled by authActionClient middleware)
4. Replace FormData extraction with destructuring from `parsedInput`
5. Replace `return { error: msg }` with `throw new Error(msg)` for server errors
6. Keep `return { success: true }` or `return { data: ... }` as-is for success cases
7. Keep all `revalidatePath()` calls
8. Keep `redirect()` calls -- test whether they work inside `.action()`. If redirect throws are caught by next-safe-action's error handler, move the redirect to be the last thing before the return (next-safe-action should let Next.js redirect errors propagate)

**Auth-specific notes:**
- `login` and `signup`: Use base `actionClient` (NOT authActionClient -- user is not yet logged in). These still need `createClient()` inside the action body since auth middleware is not used.
- `logout`: Use `authActionClient` with NO inputSchema (no input needed). Still calls `supabase.auth.signOut()` using `ctx.supabase` then redirect.
- `signInWithGoogle`: Use base `actionClient` with `signInWithGoogleSchema` (empty object). Still needs `createClient()` inside action body.

**Items-specific notes:**
- `createItem`: Uses authActionClient. Destructure `{ name, description, category, privacy, groupId }` from parsedInput.
- `deleteItem`: Uses authActionClient. Destructure `{ itemId }` from parsedInput.
- `updateItem`: Uses authActionClient. Destructure `{ itemId, name, description, category, price_usd }` from parsedInput.

**Contacts-specific notes:**
- `createContact`: Uses authActionClient. Destructure `{ name, email, phone }` from parsedInput.
- `updateContact`: Uses authActionClient. Destructure `{ contactId, name, email, phone }` from parsedInput.
- `deleteContact`: Uses authActionClient. Destructure `{ contactId }` from parsedInput.
- `linkContactToUser`: Uses authActionClient. Destructure `{ contactId, userId }` from parsedInput.

Import schemas from the colocated `./schemas` file. Import `actionClient`/`authActionClient` from `@/lib/safe-action`.

IMPORTANT: Keep the `'use server'` directive at the top of each file. Keep all existing query functions exactly as they are.

1. **Pass objects instead of FormData** for actions that previously took FormData. Extract form values and pass as typed object matching the Zod schema.

2. **Handle the new result shape.** next-safe-action returns `{ data?, serverError?, validationErrors? }` instead of `{ error?, success?, data? }`.

   - Replace `result.success` checks with `result?.data` checks
   - For field-level errors, check `result?.validationErrors`

3. **Specific component changes:**

**app/auth/page.tsx** (or wherever login/signup forms are):
- Login: Extract email/password from form, call `login({ email, password })`. Handle `serverError` for display.
- Signup: Extract name/email/password, call `signup({ name, email, password })`. Handle `serverError`.
- Note: `redirect()` inside the action may work. If it does, the component never sees a result. If it doesn't, check `result?.data` and redirect client-side.
