  <action>
Create a new migration file at `supabase/migrations/20260222000000_fix_users_rls_add_profiles_view.sql` with two changes:

**Part 1: Fix users table SELECT policy**
```sql
-- Drop the overly permissive SELECT policy
DROP POLICY IF EXISTS "Public profiles are viewable by everyone." ON public.users;

-- Replace with owner-only access
-- (SELECT auth.uid()) subquery form evaluates once per statement, not per row
CREATE POLICY "Users can view their own profile."
  ON public.users FOR SELECT
  TO authenticated
  USING ((SELECT auth.uid()) = id);
```

**Part 2: Create restricted user_profiles view**
```sql
-- Limited view exposing only id and name (never email/phone)
-- Used by server actions that need cross-user display names
CREATE VIEW public.user_profiles AS
  SELECT id, name FROM public.users;

-- Allow all authenticated users to read the view
GRANT SELECT ON public.user_profiles TO authenticated;
```

IMPORTANT: Do NOT modify any existing migrations. Do NOT touch SECURITY DEFINER functions. The timestamp in the filename (20260222000000) places it after all existing migrations.

The view approach is preferred over a SECURITY DEFINER function because:
1. It is simpler and more readable
2. Views are standard SQL that Supabase handles natively
3. The view inherits no RLS (views bypass table RLS by default in PostgreSQL) so it will work for cross-user lookups
4. It only exposes `id` and `name`, never `email` or `phone`
